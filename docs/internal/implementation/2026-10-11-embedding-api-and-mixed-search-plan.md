## 已确认的产品要求

1. API 格式由用户明确选择，选项短名为“OpenAI 兼容”“llama.cpp 多模态”“DashScope 多模态”。每项常驻显示一行介绍性文字。
2. 开启语义搜索后，默认使用语义检索；遵守既有资源库绑定规则，不把全局模型变更隐式套用到所有库。
3. 默认搜索所有已启用且支持的资产类型，按内容相关性混排，不固定偏向图片。不默认排除纯文本、拆成图文两块，或设置图片结果保留名额。
4. 2026-10-12 实施范围仅限 API 格式设置与显式请求/响应适配。默认检索切换、逐模态能力验证和排序候选不纳入本轮开发。

## API 格式与一行介绍

| 中文名称 | 中文介绍 | 英文名称 | 英文介绍 |
| --- | --- | --- | --- |
| OpenAI 兼容 | 用于文本向量服务，如 Ollama 的兼容接口。 | OpenAI compatible | For text embeddings, including Ollama's compatible endpoint. |
| llama.cpp 多模态 | 连接支持图文向量的 llama.cpp 服务。 | llama.cpp multimodal | Connect to a llama.cpp service that supports text and image embeddings. |
| DashScope 多模态 | 连接使用 DashScope 格式的多模态向量服务。 | DashScope multimodal | Connect to a multimodal embedding service using the DashScope format. |

介绍展示在对应选项名称下方，不藏进 hover 提示。沿用 `EmbeddingServiceSettings` 的设置项、单选交互、辅助文字与主题 token；不新增独立表单或 tooltip。支持的实际模态仍由具体模型验证决定，上述介绍不构成所有模型都支持图像的承诺。

协议身份继续沿用已有 OpenAI 与 DashScope adapter ID；llama.cpp 多模态使用独立的 `llamacpp-multimodal-v1`。显示名称不是 profile 或协议身份。前两项共用 endpoint 构造、鉴权和 OpenAI 响应映射，只拆分输入序列化，避免复制网络调用实现。Ollama 原生 `/api/embed` 暂不列入必要范围；内置本地 Gemma 使用应用提供的已知运行时配置，用户不重复选择协议。

### 请求与响应边界

| 格式 | 文本输入 | 图片输入 | 响应映射 |
| --- | --- | --- | --- |
| OpenAI 兼容 | `input` 字符串/字符串数组 | 本方案的标准文本格式不支持 | `data[].index` 与 `data[].embedding` |
| llama.cpp 多模态 | 标准文本输入；组合输入使用 `input[].content` | 通过 `content` 中的 `image_url` 内容片段 | 复用 OpenAI 响应映射 |
| DashScope 多模态 | `input.contents` 中的 `text` | `input.contents` 中的 `image` | `output.embeddings`，按接口合同核对 index/type/条目对应 |

首期按单资产、独立编码使用协议，不把 fusion 设为必选项。批量中的多项资产与同一资产内的图文组合是不同含义；任何组合编码必须有 adapter 与模型的显式支持。不得静默平均独立向量来模拟等价的 fusion。

内部统一接收带稳定 ID 的内容条目及 `query/document/similarity` 角色，返回按 ID 对应的向量。模型模板负责 query/document 前缀、provider instruction 和媒体预处理；不把 DashScope 的 `instruct` 或 `enable_fusion` 发给所有服务。响应按用户选择的协议解析，不通过尝试另一种响应格式来静默兜底。

配置包含格式、服务地址、模型名、可选认证、可选维度及模态声明。声明与验证分开：文本、图片等逐项验证，不以地址可达、模型名或返回 HTTP 200 作为能力通过。图片探测应使用不同内容及无图对照，证明图像确实影响向量。更改影响编码语义的配置使对应能力验证失效，并按既有 profile 与索引重建规则处理。

## 文本与图片搜索的目标

用户补充的准确现象是：含文字图片与纯文本资产普遍更容易获得高分，文字即使与查询无关也可能如此；不是只有图片印着查询关键词才靠前。受控实验与授权库对照已部分复现，证据与适用模型见上方报告，仍不能宣称全库相关性问题已解决。相关文档靠前本身不算错误；需要消除的是与查询内容无关时的普遍高分。查找海报文案、UI 文字或文档时，文字又是合法的内容证据，不能统一忽略。

此前 `scoreEmbeddings` 在混合索引内给纯文本扣固定 `0.12`，本地与 HTTP 搜索都启用；图片上的文字仍被视为 image channel，不受扣分影响。2026-10-12 已按用户要求移除此策略，不以其他校正替代，全部类型返回原始相似度。

## 候选排序方案

### 1. 统一内容表示与模型配置

使用同一已验证、兼容的 profile 编码查询和各类资产；标准 query/document 配对与媒体预处理必须正确。图片按画面编码，文本按实际内容及固定分段策略编码，不默认把图片文件名、标签或额外 OCR 文本融合进视觉向量。这样可避免人为叠加词面优势，但不能抹去模型本身读图中文字的能力。

文本-only 服务不能提供原生图像检索。绑定此类服务时须如实显示可检索范围，不把未索引图片当作语义零相关；将图片转换成描述再做文本检索属于另一种未来策略，不在本方案内隐式启用。不同模型/空间的向量不得直接比较 raw cosine。

纯文本另需处理内容覆盖：当前只编码开头 2,500 字符，授权库中 7 篇文档均发生截断。分段检索是后续待评估设计，需保留段落与资产映射、资产去重，并验证长文/多段资产不会因候选次数更多而获无关高分；不能直接以所有段落最大分替代完整方案。长文漏检与跨类型分数偏差分别验收。

### 2. 先建立针对真实症状的评估

用合成或经过脱敏与授权的 fixture 冻结三组查询：画面主体/场景查询、明确查询可见文字、纯文本与跨类型主题查询。构造成对资产：同一图像无字/相关字/无关字/随机字符，不同语言和文字面积，同样的文字叠在相关/无关画面上，以及语义相关/无关的文本资产。另准备一批主题互不相关的背景查询；文字无关的对照必须与查询无词面和语义关联，不能仅替换成另一种仍相关的表达。

标注的是内容相关性，不要求图片一定胜过文档，也不把文字占比低作为成功指标。记录逐项 Top 10、分类型 Recall@10、全类型 nDCG@10，并专项记录：同图加无关文字后的分数/名次增量，含字图片与无关文档在背景查询下的平均分数及分布，每项资产跨无关查询进入 Top 10 的频率。使用独立查询划分拟合与验证，避免在测试集上调参数。保留当前 `0.12`、无扣分 raw cosine 和后续候选方案作为对照；不把一个构造向量单测当作检索质量证据。

在排序实验之前先核对真实编码链：固定权重、mmproj、运行时、查询前缀、pooling、输出投影与归一化；用不同图片及无图对照证明图像没有被忽略。同一组 fixture 在条件允许时与官方参考实现对照，区分模型特性和运行时/预处理差异。协议字段正确或历史 canary 通过不能替代当前运行时的质量实验。若发现编码错误，先修正整条编码链并重建受影响索引，不用排序惩罚掩盖错误。

### 3. 无重排服务时：以评估选择模型与校准

Embedding-only 模式必须独立可用。先测试官方查询模板、可用模型及预处理，选择对上述三组查询表现合格的配置。Gemma 官方短前缀与支持自定义 instruction 的模型不是同一种能力；不得假设任意长指令都能要求 Gemma 忽略文字，也不采用无条件“视觉优先”指令。

若观察到稳定的跨类型分数尺度差异，可在标注集上拟合并验证按模型/profile 的相关性校准或学习排序。使用 channel 特征时只允许有证据的分数校正，不把“图片比文字重要”作为训练目标。校准器与排序策略版本化，旧模型上的参数不能套给新模型；校准方式、特征与数值由评估决定，不在本文拍定。

如果少数资产在大量不相关查询下都稳定高分，应检验跨模态检索中的 hubness 现象，并对照 Querybank Normalisation（QB-Norm）类方法：依据独立背景查询估计每项资产普遍被匹配的倾向，尝试校正这一偏差。不是按“有字”或“是文本”扣分；同样普遍高分的无字图片也应接受同一规则。背景查询需来自合成/脱敏评估集，不把用户搜索历史默认持久化；校准预算、失效条件和增量更新规则须与 profile/策略版本绑定。QB-Norm 有研究依据，但对当前模型效果尚未验证；查询分布不匹配也可能损害质量，不能直接采用拍定的减均值或固定常数。[跨模态检索与 Querybank Normalisation](https://arxiv.org/abs/2112.12777)

仅按大类修改分数尺度不能证明同一图像通道里的含字图片偏差已消除。若校正后仍稳定失败，应记录该模型的质量限制，继续评估替代模型或进入下一步，不能宣称调分已解决。

### 4. 可选增强：统一多模态重排

对候选的真实内容使用同一个支持文本与图像的 reranker：文本候选提供文本，图像候选提供图片，由 query 与候选内容联合判断相关性。不将图片只转换成 OCR 字符串交给文本 reranker；也不比较多个不同 reranker 的原始分数。

候选召回可按 channel 分别扩大候选池，以免一类资产在原始分数阶段完全挤掉另一类；这是召回覆盖策略，不是最终结果的类型配额。候选预算以 Recall 和延迟实测决定。reranker 无法找回未进入候选池的相关资产，也可能继续偏重文字，必须对同一冻结评估集验证。

重排是独立可选能力，不要求 embedding provider 同时提供。输入模态、指令、限额与输出分数合同单独验证。请求失败时明确显示问题并保留已有结果，允许使用基础排序；不把失败写成成功且零结果。用户未配置重排时使用通过评估的 embedding-only 排序，不自动上传候选内容至其他服务。

### 5. 本次不采用的默认做法

- 不固定降低纯文本分数，不按含字面积给图片扣分，不设图片优先或最终类型配额。
- 不把 RRF 当作该问题的充分修复：互不重叠的图文候选列表按名次融合，可能只是交错输出，丢失相关性强弱；它不证明全类型相关性准确。
- 不默认遮字或抹字。海报、UI、文档截图的文字本身可能是核心内容，修改图像表示需独立产品与质量验证。
- 不把 fusion、升级 API 格式或协议探测成功当作检索质量证据。

最终候选排序都复用既有过滤、稳定分页与索引代次机制，最新查询才能更新画布；已显示结果不因后台索引更新无提示重排。

## 实施顺序与复用位置

1. 先交付 API 短名、一行介绍、显式多模态扩展及逐模态验证；这是接入改进，不作为相关性修复验收。
2. 建立含字与无字、相关与无关的图文混合质量基线，先检查真实编码链，再比较当前扣分、无扣分、跨类型校准与资产背景相似度校正。默认语义搜索行为复用现有绑定与搜索 controller。
3. 以评估结果选择基础排序，并退役固定文本扣分。若无法满足含字图片专项要求，保留未解决记录与下一步方案，不关闭问题。
4. 用户需要且服务能力具备时，另交付多模态重排接入与真实质量/性能验证；不阻塞基础 API 接入。

优先复用 `src/shared/embedding/http-service.ts`、`modalities.ts`、`profile.ts`，`src/main/embedding-http.ts`、`embedding-llama-session.ts` 与既有 service registry；设置复用 `EmbeddingServiceSettings`，默认语义行为复用 `semantic-work`/`semantic-browse`。排序与校准应抽取独立模块，不继续膨胀 `App.tsx` 或把全套逻辑堆进实验索引类。
